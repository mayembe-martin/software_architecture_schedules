Iker:

1) Availability Problem: A Student wants to check a grade from the Web Application, but in the Backend API, the Persistence Adapter is not returning to the Result Viewing the grade mark.

Solution: The systems sends both to the teacher and to the Student a notification that the system is not working. In the case of the teacher, he Will receive a notification from the system that is not working, and a reminder of sending personally to the Student the pertinent grade. In the case of the Student, the system Will send him a notification of the system not working along with a notification that the teacher Will send him the grade personally.


2) Modifiability problem: The grading system must be modified in order to include a new feature, and the IT deparment must do it within an hour (time). However, when the IT deparment examinates the system they realise that the data Flow of the grading service is merged with other data flows of the rest of the services into one Persistence Adapter, right before Reading information of the DataBase. The problema is that if one data Flow wants to be modified, every data Flow must be also modified and this makes the modification of the system something far more complex and that takes much more time that the established time (1 hour).

Solution: To make the system more modifiable, the unique persistent adpater can be splited in many independent adapters, one for each service's data Flow. With this, every time one data Flow needs to be modified, it can be done idependently from the other data flows and in the time lapse required (in this case, 1 hour).

Requirement: 
Enable independent deployment of components with comprehensive automated testing, supporting bi-weekly releases with minimal downtime.

Architectural Extension: None Required.

a) Clean Separation of Concerns:
- Clear component boundaries with single responsibilities (Term Management, Registration, Grading, Results)
- Hexagonal/ports-and-adapters pattern evident (Persistence Adapter, Integration Adapter)
- Components communicate through well-defined interfaces

- Integration Adapter abstracts external systems - can be mocked for unit testing
- Persistence Adapter abstracts database - enables in-memory testing
- Each component has clear inputs/outputs suitable for contract testing
- Dynamic views document interaction flows useful for integration test scenarios

- Web Application (SPA) can be deployed separately from Backend API
- Component-level separation within API container allows for future microservices extraction
- Database schema changes can be managed through migration scripts independently


d) Development Environment Support:
- Dedicated development deployment environment shown
- Test instances of external systems enable isolated testing

Yash Mange : 

* Reliability problem : 

During peak usage (e.g. after grade publication or before exam registration deadlines), external systems such as the Student Information System (SIS) or the Timetable Service may become temporarily unavailable or respond slowly.
When this happens, core EXA functionality (registration, result viewing, or grading workflows) may fail or hang due to synchronous dependencies on these external services.

-Involved Users:
Student, Teacher

-Affected System Parts:
--In Backend API:

Integration Adapter

Registration Management

Grading Management

Result Viewing

--In External Systems:

Student Information System (SIS)

Timetable Service

The current architecture allows failures in external systems to propagate into EXA, reducing overall system reliability and potentially blocking critical academic processes.


* Reliability problem solution : 

The solution introduces fault-tolerance mechanisms at the Integration Adapter level.
All communication with external systems is guarded by timeouts, retries with backoff, and circuit breakers.

If an external system is unavailable, the Integration Adapter either:

returns cached or last-known-valid data where possible, or

fails fast and allows the calling business component to continue in a degraded but controlled mode.

This prevents cascading failures, ensures that EXA remains operational for core use cases, and significantly improves system reliability even when external dependencies are unstable.



* Scalability problem issue :

At predictable times such as the beginning of the semester or during exam registration openings, hundreds or thousands of students may simultaneously attempt to register for exam terms or view schedules.
This leads to sudden spikes in load on the Backend API, particularly on registration-related components and database access.

-Involved Users:
Student

-Affected System Parts:
--In Backend API:

Registration Management

Persistence Adapter

Database

--In Infrastructure:

Backend API container

The current architecture risks performance degradation or request failures under high concurrent load if backend components cannot scale quickly enough.

* Scalability problem solution :

The solution leverages horizontal scalability of the Backend API container.
The Registration Management component is designed to be stateless, allowing multiple instances to be deployed behind a load balancer.

Database access is optimized through connection pooling and efficient transaction handling, while predictable peak periods are handled by pre-scaling backend instances ahead of time.

This approach ensures that the system can handle large bursts of concurrent requests while maintaining acceptable response times, fulfilling the scalability requirement.
