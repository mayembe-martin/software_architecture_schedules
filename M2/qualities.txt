AVALABILITY PROBLEM
1) Requirement: After having the marks of an exam, the system must receive the uploaded marks from the teacher and must display them 
    within a maximum of 15 minutes.

    Problem: When the system recieves the marks from the teacher, it does not always process them correctly and, as a consequence, 
    the marks are not displayed to the students in time (15 min).

    Solution: After the upload of the marks by the teacher, the system performs a validation process lasting up to 1 minute.
    This is achieved by implementing a Grade Publisher Monitor container in the Web Application layer of the architecture.
    If the validation fails, a notification is sent to the teacher informing that the marks have not been correctly published,
    so corrective action can be taken in order to meet the 15-minute margin.
    If the validation succeeds, the Grade Publisher Monitor sends a confirmation notification to the teacher indicating that the 
    marks have been correctly published.

    Source of stimulus: Results Views component (Web Application), requesting updated exam marks for student visualization.
    Stimulus: Results Views requests the publication and availability of newly uploaded exam marks from the Web Application.
    Environment: Normal system operation, with internal container communication enabled between Web Application and Backend API.
    Artifact: Web Application – Grade Publisher Monitor container.
    Response: Validation from the Grade Publisher Monitor, if succeded confirmation, if failed notification of failure.
    Measure: Validation < 1 min. Mark availability < 15 min.

MODIFIABILITY PROBLEM
2) Requirement: The grading system must be modifiable to include a new feature, and the IT department must be able to implement 
   the change within a maximum of 1 hour.

    Problem: When the IT department analyses the system, they identify that the data flow of the Grading Management component 
    is merged with the data flows of other backend services into a single shared Persistence Adapter before accessing the Database.
    As a consequence, any modification in the grading data flow requires changes in the shared persistence logic, impacting multiple 
    services. This tight coupling increases complexity, regression risk, and testing effort, making it impossible to perform the 
    modification within the required 1-hour time limit.

    Solution: To improve modifiability, the single shared Persistence Adapter is split into multiple independent persistence adapters,
    one per service data flow. With this separation, changes in the grading data flow affect only the Grading Persistence Adapter 
    and the Grading Management component, other services remain untouched and the time requiered to do any modification in any data 
    flow is significantly reduced, allowing the change to be implemented within the 1-hour constraint.

    Source of stimulus: IT Department / Maintenance Engineer.
    Stimulus: A request to modify the Grading Management functionality to include a new feature.
    Environment: System in maintenance mode, with access to the Backend API source code, automated build pipeline, and test environment.
    Artifact: Backend API – Grading Management component and its dedicated Grading Persistence Adapter
    Response: The IT department modifies only the grading-related business logic and its dedicated persistence adapter.No changes are required in persistence adapters of other services
    Measure: Modification < 1 hour. Only grading-related components and adapters are changed.

Yash Mange : 

* Reliability problem : 

During peak usage (e.g. after grade publication or before exam registration deadlines), external systems such as the Student Information System (SIS) or the Timetable Service may become temporarily unavailable or respond slowly.
When this happens, core EXA functionality (registration, result viewing, or grading workflows) may fail or hang due to synchronous dependencies on these external services.

-Involved Users:
Student, Teacher

-Affected System Parts:
--In Backend API:

Integration Adapter

Registration Management

Grading Management

Result Viewing

--In External Systems:

Student Information System (SIS)

Timetable Service

The current architecture allows failures in external systems to propagate into EXA, reducing overall system reliability and potentially blocking critical academic processes.


* Reliability problem solution : 

The solution introduces fault-tolerance mechanisms at the Integration Adapter level.
All communication with external systems is guarded by timeouts, retries with backoff, and circuit breakers.

If an external system is unavailable, the Integration Adapter either:

returns cached or last-known-valid data where possible, or

fails fast and allows the calling business component to continue in a degraded but controlled mode.

This prevents cascading failures, ensures that EXA remains operational for core use cases, and significantly improves system reliability even when external dependencies are unstable.



* Scalability problem issue :

At predictable times such as the beginning of the semester or during exam registration openings, hundreds or thousands of students may simultaneously attempt to register for exam terms or view schedules.
This leads to sudden spikes in load on the Backend API, particularly on registration-related components and database access.

-Involved Users:
Student

-Affected System Parts:
--In Backend API:

Registration Management

Persistence Adapter

Database

--In Infrastructure:

Backend API container

The current architecture risks performance degradation or request failures under high concurrent load if backend components cannot scale quickly enough.

* Scalability problem solution :

The solution leverages horizontal scalability of the Backend API container.
The Registration Management component is designed to be stateless, allowing multiple instances to be deployed behind a load balancer.

Database access is optimized through connection pooling and efficient transaction handling, while predictable peak periods are handled by pre-scaling backend instances ahead of time.

This approach ensures that the system can handle large bursts of concurrent requests while maintaining acceptable response times, fulfilling the scalability requirement.
